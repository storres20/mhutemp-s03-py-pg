# MHUTEMP Stack 03 Backend

Python/FastAPI and PostgreSQL backend implementation of the **MHUTEMP healthcare environmental monitoring architecture**.

Stack 03 was developed as an alternative implementation of the MHUTEMP Persistence Layer to evaluate whether the same functional monitoring workflow can be preserved after replacing **MongoDB** with **PostgreSQL**, while retaining **Python/FastAPI** as the Processing Layer technology.

---

## Architecture

The Stack 03 experimental configuration is:

```text
ESP32 Monitoring Node
        |
        | WebSocket / HTTP
        v
Python / FastAPI Backend
        |
        v
PostgreSQL
```

The architectural responsibilities evaluated in Stack 03 are:

| Layer | Technology |
|---|---|
| Acquisition | ESP32 |
| Communication | WebSocket / HTTP |
| Processing | Python / FastAPI |
| Persistence | PostgreSQL |
| Presentation | Not included in the persistence-substitution test |

Stack 03 specifically evaluates the **Acquisition-to-Persistence path** in order to isolate the Persistence Layer technology substitution.

---

## Purpose

Stack 03 is part of the experimental evaluation of the **MHUTEMP reference software architecture**.

The main objective of this implementation is to evaluate a selected **Persistence Layer technology substitution**:

```text
Stack 02
Python / FastAPI + MongoDB

              |
              | Persistence technology substitution
              v

Stack 03
Python / FastAPI + PostgreSQL
```

Python/FastAPI is retained as the Processing Layer implementation while the persistence technology is changed from MongoDB to PostgreSQL.

The acquisition hardware, firmware, communication mechanism, and monitoring message structure remain unchanged.

This experiment provides practical evidence supporting **technology independence for the evaluated Persistence Layer substitution**.

It does not imply universal technology independence or performance equivalence between MongoDB and PostgreSQL.

---

## Experimental Evaluation

A physical MHUTEMP monitoring node was connected to the Stack 03 backend using the same:

- ESP32 acquisition hardware
- firmware
- sensing configuration
- WebSocket communication mechanism
- JSON message structure

used in the Stack 02 experiment.

During the evaluated continuous experimental session:

| Parameter | Result |
|---|---:|
| Test duration | 14 min 09 s |
| Persisted monitoring records | 414 |
| Median inter-record interval | 2.0 s |
| Processing backend | Python / FastAPI |
| Database | PostgreSQL |
| Acquisition node | ESP32 |
| Communication | WebSocket / HTTP |

The experiment demonstrated that monitoring records generated by the same physical node could be received through the Python/FastAPI backend and persisted in PostgreSQL while preserving the expected Acquisition-to-Persistence monitoring flow.

No performance equivalence between MongoDB and PostgreSQL is claimed.

## Relationship with the MHUTEMP Experimental Stacks

Three technology configurations were considered in the architectural evaluation:

| Stack | Processing | Persistence | Experimental Purpose |
|---|---|---|---|
| Stack 01 | Node.js / Express | MongoDB | Operational baseline |
| Stack 02 | Python / FastAPI | MongoDB | Processing Layer substitution |
| **Stack 03** | **Python / FastAPI** | **PostgreSQL** | **Persistence Layer substitution** |

The experimental strategy is:

```text
STACK 01
Node.js / Express
MongoDB
      |
      | Processing substitution
      v
STACK 02
Python / FastAPI
MongoDB
      |
      | Persistence substitution
      v
STACK 03
Python / FastAPI
PostgreSQL
```

Therefore:

- **Stack 01 → Stack 02** evaluates a selected substitution of the **Processing Layer** technology.
- **Stack 02 → Stack 03** evaluates a selected substitution of the **Persistence Layer** technology.

Stack 03 was specifically designed to isolate the second substitution.

---

## Persistence Layer Substitution

The principal experimental change evaluated by Stack 03 is:

```text
Processing Layer
Python / FastAPI
        |
        v

STACK 02                  STACK 03

MongoDB        ----->     PostgreSQL
Persistence               Persistence
```

The experiment retains the same Python/FastAPI Processing Layer and monitoring message structure while replacing the database technology.

This separation allows the Persistence Layer substitution to be evaluated without simultaneously changing the Processing Layer implementation.

## Monitoring Information Flow Model

The MHUTEMP reference architecture is derived from a **Monitoring Information Flow Model (MIFM)**.

The model represents the transformation of monitoring information as:

```text
Physical Observation
        |
        v
Digital Measurement
        |
        v
Processed Information
        |
        v
Historical Record
        |
        v
Decision-Support Information
```

These stages are mapped to five architectural responsibilities:

```text
Acquisition
    |
    v
Communication
    |
    v
Processing
    |
    v
Persistence
    |
    v
Presentation
```

The architectural responsibilities are defined independently of the specific technologies used to implement them.

Stack 03 evaluates whether the **Persistence responsibility** can be implemented using PostgreSQL while preserving the preceding monitoring information flow.

## Scientific Context

This repository supports the reproducibility of the revised research study:

**MHUTEMP-ULT: An Open-Source IoT System for Ultra-Low Temperature Monitoring of Plasma Storage in Healthcare Facilities**

The study proposes a technology-independent layered reference software architecture derived from a **Monitoring Information Flow Model (MIFM)**.

The architecture separates the healthcare environmental monitoring workflow into five functional responsibilities:

1. Acquisition
2. Communication
3. Processing
4. Persistence
5. Presentation

Stack 03 provides an alternative implementation of the **Persistence Layer** using PostgreSQL while retaining Python/FastAPI as the Processing Layer technology.

## Reproducibility Scope

The Stack 03 experiment demonstrates that the evaluated Acquisition-to-Persistence monitoring workflow can operate after substituting:

```text
MongoDB
   ↓
PostgreSQL
```

while retaining:

```text
Python / FastAPI
```

as the Processing Layer technology.

The experimental results should **not** be interpreted as:

- proof of universal technology independence;
- formal validation of modularity;
- formal validation of maintainability;
- proof of performance equivalence between MongoDB and PostgreSQL;
- evidence that technology substitution requires no implementation effort;
- validation of scalability under arbitrary workloads;
- validation of the Presentation Layer after PostgreSQL substitution.

The experiment specifically evaluates preservation of the proposed functional organization under the selected **Persistence Layer technology substitution**.

---

## Experimental Scope of the Presentation Layer

The Stack 03 experiment was designed specifically to isolate the persistence technology substitution.

For this reason, experimental verification covered:

```text
Acquisition
    |
Communication
    |
Processing
    |
Persistence
```

The **Presentation Layer was not independently re-evaluated** after replacing MongoDB with PostgreSQL.

The end-to-end Presentation Layer integration was evaluated separately in Stack 02 using the Next.js monitoring interface.
